01  github.com issue #107757 + HN thread, Nov 5-6 · HN: 704 points at 06:30 IST

📮 Claude Code puts the user’s email in outbound web requests - a fix is claimed, users can’t find it

A bug report filed Thursday night says Claude Code "divulged my email to arbitrary 3rd parties in the User-Agent request header" while conducting web searches. Overnight it became HN’s #1 story. A responder whose fix commit carries an anthropic.com co-author line says a deterministic block shipped in v2.1.317 - users on v2.1.318 report no such plugin. The mod’s source is now in the repo.
SCENE

Thursday, 22:13 UTC: issue #107757 lands on anthropics/claude-code - "Bug Report: Privacy violation in User-Agent header." The reporter, taylor-edwards, says he receives "dozens of scam emails per day because claude code divulged my email to arbitrary 3rd parties in the User-Agent request header while conducting web searches without my permission," on version 2.1.318, and says he is migrating his company off Anthropic. By 06:30 IST the Hacker News thread sits at #1 with 704 points and 242 comments.

THE THING

The thread reconstructed the mechanism within the hour. Sites like Wikipedia and the SEC ask automated clients to identify themselves with a contact email in the User-Agent; commenter varenc demonstrated the SEC’s API returning 403 to a default curl and 200 to a User-Agent carrying an email (his later edit: the SEC accepts most non-curl agents, so the email is not truly required). Claude, asked to research, complies - with the signed-in account’s real address, and without asking. The fix-side response came from the poteat account: "nobody implemented this ‘share email addresses to websites’ as a feature. Models can be highly unpredictable," and a built-in mod, cc-plugin-privacy, "deterministically" blocks the behavior in v2.1.317 and later, on by default. The claim is checkable and we checked: commit 90380ef, co-authored by atp@anthropic.com, adds mods/privacy to the repo, and its README says it "refuses a shell call that holds the signed-in account’s email address and names a User-Agent, with no prompt." The gap: the reporter is on 2.1.318, and commenter francescor, also on 2.1.318, writes "I cannot see any cc-plugin-privacy in /plugins." The history is longer than one bad week: issues #81138 (July), #78431 (August, its own 38-point HN thread), #55743 (May - the account email auto-injected into model context with no opt-out, per a commenter’s list) and #101659, referenced in the thread. Two cautions. The mod blocks shell calls that name a User-Agent; a companion Tell HN describes a different path - the email sits in the model’s context and the model pastes it into requests - which this check does not obviously cover. And the scam-flood itself is the reporter’s account: one HN user reports the same correlation, another argues coincidence, since Wikipedia and the SEC do not sell addresses. This is day four of the consent thread: Postman’s silent installs (No. 032), the Codex toggle self-report (No. 032), Gemini’s training fine print (No. 033), and now the agent’s own outbound identity.

✂️ STEAL IT

Steal the threat model: any website can ask a well-behaved agent for your contact details, and a well-behaved agent does not lie about them. Your agent’s outbound identity is your data policy, and the default is "helpful." Set the allowlist yourself - one commenter’s CLAUDE.md permits the email only to named domains, asks first everywhere else, and sends a tool-named UA otherwise (linked from the issue thread).

Try today  VERDICT

Do the TRY section below: update, check /plugins, pin your own User-Agent rule, and watch what your agent actually sends to a request bin. It fails you as confirmation of the scam-flood claim, which remains one reporter’s account - and as settled proof that the fix works, since users on the supposedly fixed version report no privacy mod.

02  sshhole.com write-up, Nov 5 · HN: 2,441 points at 06:30 IST

🔓 sshole: on musl Linux, locked SSH accounts accept any password over 256 characters

A 2012 musl commit, a 256-byte key cap and Alpine’s star-locked root combine into a ten-year bypass across Alpine, OpenWrt, Buildroot and Yocto - a big slice of the Docker base-image world. Fixed in OpenSSH 10.6p2. 2,441 HN points - and the finder credits "agent swarms. a lot of them."
SCENE

"oh did i say ‘i’? sorry. i had agent swarms. a lot of them. let’s not get into it." The author of sshhole.com built OpenSSH every way he could think of - glibc, musl, PAM, no PAM, shadow, no shadow - and threw some 17,600 weird logins at the matrix. Every build agreed on every login except musl-without-PAM, which said yes to things it should not.

THE THING

The chain, per the write-up: in August 2012 musl changed crypt() to return the string "*" instead of NULL on failure, so callers that never checked for NULL stopped crashing. Twenty days later musl added sha512 crypt with a 256-byte key cap as DoS protection - longer passwords make crypt() fail, and failure now returns "*". An account locked with "*" in /etc/shadow - root on Alpine since 3.16, key-only deploy users, LDAP users - therefore accepts any password of 257 to 1,024 characters where sshd runs on musl without PAM, password logins are on, and some other account has a real password. On Alpine’s official AWS and Azure images, the default alpine user qualifies and has passwordless doas: "so it’s root." The near-misses are the best part: a Debian dev once asked glibc to copy musl’s "*" and Debian ended up one character away ("*0"); an OpenSSH security review this October fixed pick_salt() four lines above the bug "four days before i found it." The fix shipped: OpenSSH 10.6p2. The mitigation: PasswordAuthentication no. glibc, PAM, Dropbear and OpenBSD are unaffected. 2,441 HN points - the biggest story on the board.

✂️ STEAL IT

Steal the method: the finder is explicit that agent swarms did the sweeping - parallel agents fuzzing a boring build matrix found what ten years of human review stepped over, four lines from a fresh security fix. Cheap parallel agents are becoming an audit instrument; the teams that point them at their own dependencies first get the findings before the front page does.

Try today  VERDICT

If you run sshd on Alpine, OpenWrt, Buildroot or Yocto: apk upgrade openssh (10.6p2), or set PasswordAuthentication no and restart - then check auth logs for a password login by an account that has no password; the write-up links a checker at github.com/oz9un/sshole. It fails you if your sshd runs on glibc or through PAM, which is most server Linux.
